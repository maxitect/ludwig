# Database Rules

Full model: `docs/SPEC.md` section 7.4. These rules are non-negotiable. A schema PR that breaks one is rejected.

## Normalisation

- **3NF.** Every non-key column depends on the key, the whole key and nothing but the key.
- **Don't store anything derivable.** Compute it in `src/puzzles/<type>/derive.ts`. Examples: crossword answers and clue numbers, sudoku solutions, ciphertexts, maze paths, gear spin signs, hint counts, streaks.
- **Atomic cells only.** No `jsonb`, `json`, array, or delimited or encoded text columns, so no FEN strings and no "4,3" enumerations. Composite data becomes child rows keyed by `(parent_id, position)` or coordinates.
- **Controlled redundancy** is allowed only when the database keeps it consistent:
  - a composite FK to the source of truth;
  - plus a `BEFORE INSERT` fill trigger if the app would otherwise have to supply the value.

  App code never writes or syncs a redundant value. Add every new case to `docs/SPEC.md` section 7.4.5.

## Relationships

- **No polymorphic relationships.** Every FK targets exactly one table. Never add `(target_type, target_id)` columns.
- **Subtypes use class-table inheritance:**
  - `<type>_puzzles.puzzle_id` is both the PK and the FK.
  - `type_key text GENERATED ALWAYS AS ('<type>') STORED`.
  - Composite FK `(puzzle_id, type_key)` → `puzzles (id, type_key)`, `ON DELETE CASCADE`.

  Attempts follow the same pattern: `<type>_attempts` → `attempts (id, type_key)`.

- **Same-puzzle references** use composite FKs, e.g. `(puzzle_id, killer_gear_id)` → `gear_puzzle_gears (puzzle_id, id)`. That way a child can never point at another puzzle's rows.

## Enums, lookups and checks

- Use a `pgEnum` for a fixed option set that carries only a name.
- Use a **lookup table** only when options carry extra attributes or must be extensible without a migration. Current lookups: `puzzle_categories`, `puzzle_types`, `pictogram_glyphs`, `words`. Don't add one without a stated reason.
- Use a `CHECK` only where an enum is impossible, i.e. numeric domains such as `difficulty BETWEEN 1 AND 5`, ranks 1–8 and tooth counts.

## Solution columns

- Mark solution columns `(S)` in the spec.
- Play queries in `load.ts` name their columns explicitly and never select **(S)** columns.
- Only `load-solution.ts` and `check.ts` read them.

## Drizzle

- Core tables live in `src/db/schema/core.ts` and `progress.ts`. Per-type tables are in `src/puzzles/<type>/tables.ts`, and everything is re-exported from `src/db/schema/index.ts`.
- Relations are declared in `src/db/relations.ts` with RQBv2 `defineRelations`.
- Trigger-filled columns are declared as `.notNull().default(sql\`NULL\`)`, so insert types treat them as optional.
- Triggers and functions go in custom migrations (`pnpm drizzle-kit generate --custom --name=<concern>`). Use `/db-trigger`.
- Never edit a migration after it has merged. Migrations must be backward-compatible with the previous deploy.
- `src/db/auth-schema.ts` is generated by the Better Auth CLI. Regenerate it; never hand-edit it.

## Tests

Every constraint, trigger and composite FK needs a Vitest integration test against local Postgres. The test proves that valid data passes and that the drift or misuse it guards against fails.
