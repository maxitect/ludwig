# T003: Spike S1, Drizzle 1.0 RC + Better Auth + auth schema

## Context

This proves the riskiest pre-release combination, Drizzle 1.0 RC with Better Auth 1.7, and lands the real database and auth plumbing that later tickets build on. See PLAN §3 M0 S1. It's a spike in name only: everything in scope is kept.

## Scope

**In**

- Dependencies, at exact versions with no `^`:
  - `drizzle-orm@rc` and `drizzle-kit@rc`, pinned to the resolved `1.0.0-rc.x`;
  - `pg` and `@types/pg`;
  - `@vercel/functions`;
  - `better-auth`.
- `src/db/index.ts`:
  - a module-level `pg.Pool` from `env.DATABASE_URL` (`max: 5`, short `idleTimeoutMillis`);
  - `attachDatabasePool(pool)` when `process.env.VERCEL` is set;
  - `drizzle({ client: pool, schema, relations, casing: "snake_case" })`.
- `src/db/schema/index.ts` re-exporting `../auth-schema`. Also `src/db/relations.ts`, holding auth relations only.
- `drizzle.config.ts`:
  - dialect `postgresql`;
  - schema `src/db/schema/index.ts`;
  - output `drizzle/`;
  - `casing: "snake_case"`;
  - `dbCredentials.url` set to `DATABASE_URL_UNPOOLED`.
- `src/lib/auth.ts`, configured per SPEC §7.3:
  - drizzle adapter with `provider: "pg"`;
  - email and password with `requireEmailVerification: false`;
  - session settings;
  - `rateLimit: { enabled: true, storage: "database" }`;
  - `advanced.database.generateId: "uuid"`;
  - `plugins: [nextCookies()]`.
- `src/lib/auth-client.ts`.
- `src/app/api/auth/[...all]/route.ts`.
- `src/db/auth-schema.ts`, generated by the Better Auth CLI. Don't hand-edit it.
- `db:generate`, `db:migrate` and `db:studio` scripts made real. Generate and commit the first migration.

**Out**

- Sign-in and sign-up pages and actions, `proxy.ts`, `getCurrentUser` and custom rate-limit rules (T008).
- App tables (T004).

## Notes

- **CLI name.** Check the Better Auth 1.7 docs for the current CLI command, likely `pnpm dlx @better-auth/cli generate --config src/lib/auth.ts --output src/db/auth-schema.ts`. Record the exact command in a comment at the top of `auth-schema.ts`, and in the report.
- **Table names.** Tables must be `user`, `session`, `account`, `verification` and `rate_limit`. If the CLI emits `rateLimit`, set `rateLimit.modelName` or the model `modelName` option so the table is `rate_limit`. Columns are snake_case through Drizzle `casing`.
- **RQBv2.** Read the Drizzle 1.0 docs (`defineRelations`, `drizzle({ client, relations })`) and the v3 migrations folder layout. The `drizzle-orm/zod` import path must resolve. A one-line typecheck usage in a test is enough.
- **Fallback (PLAN §7).** If the RC breaks generation, migration, the adapter or the typecheck and the problem can't be fixed within the cycle cap:
  - switch to `drizzle-orm@0.45` / `drizzle-kit@0.31` and `drizzle-zod@0.8`;
  - make the matching edit to SPEC §7.1 and CLAUDE.md, recording the decision;
  - list it under Deviations in the report.
- **Test emails.** Use the `t003-<n>@test.local` pattern (INSTRUCTIONS §3).

## Acceptance criteria

- [ ] **AC1**: Drizzle and drizzle-kit are pinned to an exact version with no range.
  - _Verify (code):_ `node -e "const p=require('./package.json');console.log(p.dependencies['drizzle-orm'],p.devDependencies['drizzle-kit'])"` prints two exact versions, with no `^` or `~`.
- [ ] **AC2**: Migrations apply to a fresh database and create exactly the Better Auth tables.
  - _Verify (db):_ on a fresh `ludwig_t003`, `pnpm db:migrate` exits 0. `psql "$DATABASE_URL" -c "\dt public.*"` lists `user`, `session`, `account`, `verification` and `rate_limit`, plus nothing else except the Drizzle migrations table.
- [ ] **AC3**: Auth tables have no `jsonb` or array columns, and ids are uuid.
  - _Verify (db):_ `select table_name,column_name,data_type from information_schema.columns where table_schema='public' and (data_type in ('jsonb','json','ARRAY'))` returns 0 rows. `select data_type from information_schema.columns where table_name='user' and column_name='id'` returns `uuid`.
- [ ] **AC4**: Sign-up via the API creates a user, a credential account with a hashed password, and a session.
  - _Verify (api + db):_ run `curl -i -c .verification/T003/c.txt -H 'content-type: application/json' -d '{"email":"t003-1@test.local","password":"correct-horse-battery","name":"Tester"}' http://localhost:3003/api/auth/sign-up/email`. Expect a 200 and a `Set-Cookie` with the session token. Then `select provider_id, password like '%:%' as hashed from account join "user" u on u.id=account.user_id where u.email='t003-1@test.local'` returns `credential | t`, and `select count(*) from session` returns at least 1.
- [ ] **AC5**: Sign-in works with the correct password and fails with a wrong one.
  - _Verify (api):_ `POST /api/auth/sign-in/email` with the correct password returns 200 and `Set-Cookie`. With `wrong-password-123` it returns 401 and no session cookie.
- [ ] **AC6**: The session cookie resolves to the user.
  - _Verify (api):_ `curl -b .verification/T003/c.txt http://localhost:3003/api/auth/get-session` returns JSON whose `user.email` is `t003-1@test.local`. Without the cookie it returns `null`.
- [ ] **AC7**: The rate-limit table is used, which proves database storage rather than memory.
  - _Verify (db):_ after AC5, `select count(*) from rate_limit` returns at least 1.
- [ ] **AC8**: `drizzle-orm/zod` and RQBv2 relations typecheck.
  - _Verify (unit):_ `src/db/db.test.ts` builds `createSelectSchema(user)`, parses a sample row, and runs `db.query.user.findFirst({ with: { sessions: true } })` against the test database. It passes.
- [ ] **AC9**: The DB client only attaches the Vercel pool helper on Vercel.
  - _Verify (code):_ `grep -n "attachDatabasePool" src/db/index.ts` shows the call guarded by `process.env.VERCEL`.
- [ ] **AC10**: Gates pass, and any fallback decision is recorded.
  - _Verify (cli):_ `pnpm typecheck && pnpm lint && pnpm test && pnpm build` exits 0. The report states either "RC retained" or "fallback taken", with the SPEC §7.1 diff.
