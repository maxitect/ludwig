## Rate-limit mechanism and client IP

- Better Auth's limiter (`onRequestRateLimit`) runs only in `auth.handler`, not in `auth.api.*`. The `signIn` action therefore builds a `Request` to `${BETTER_AUTH_URL}/api/auth/sign-in/email` carrying the incoming request headers (`headers()`), and calls `auth.handler`. The 5 per 15 min custom rule in `src/lib/auth.ts` (database storage) then applies to the form exactly as to the API. 429 maps to a form error using `x-retry-after`; any other failure to "Invalid email or password."
- `nextCookies()` deliberately skips handler-originated calls (`_flag === "router"`), so the action copies `Set-Cookie` onto `cookies()` using Better Auth's own `parseSetCookieHeader` / `toCookieOptions` (same logic as the plugin). Verified: sign-in via the form sets the session.
- Client IP: Better Auth's `getIP` reads `x-forwarded-for` (default `ipAddressHeaders`); with no `trustedProxies` it only trusts a single-value header. On Vercel the edge sets `x-forwarded-for` to the single client IP, so this resolves correctly and the action and HTTP paths share the key `<ip>|/sign-in/email`. In development with no header it falls back to 127.0.0.1; in production with no trustworthy IP it falls back to one shared `no-trusted-ip` bucket (logged warning). No config change was made; confirm on a Vercel preview that the warning does not appear.
- Sign-up through the action still calls `auth.api.signUpEmail` (no limiter; out of ticket scope, which only specifies a sign-in rule).
