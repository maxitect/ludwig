## Design decisions

- **One write path.** `scripts/seed.ts` now exports `upsertPuzzle(db, registry, { typeKey, meta, content })`, the former loop body unchanged in behaviour, returning `{ id, inserted }`. `seed()` calls it directly; `generate-gears.ts` calls it inside a transaction that also inserts the `gear_daily` row, so a puzzle is never left unlinked.
- **`db:seed` vs daily puzzles.** Seed deletes puzzles of a registered type whose slug has no content file, except those linked in `gear_daily` (changed in review from a `daily-` slug-prefix rule, which also protected stale `daily-*` rows of any type). gen-gears never touches content files, so the two do not fight.
- **`published_at`** is the start of the date in `Europe/London` (`src/utils/london-time.ts`, tested around both clock changes), so future dailies are hidden by the catalogue's `isPublished`. **Volume:** none. **Puzzle title:** `Daily Diagram <date>`. **Difficulty column:** preset index + 2 (easy 2, medium 3, hard 4, expert 5).
- **Existing dates are skipped, not rewritten.** The seed path deletes the subtype row before reinserting, which cascades to the puzzle's `gear_attempts`, so re-running would wipe players' saved progress on a live daily. Skipping makes the re-run idempotent (AC2). Tradeoff: after retuning presets, existing dailies are not regenerated unless their rows are dropped first (AC3 flow). The ticket text says "upserts"; the upsert path is still used for every date that is not yet materialised.
- **DB verification** lives in `scripts/verify-puzzles.ts` (`verifyGeneratedRows`): it reads every `gear_daily` puzzle through the gears module's server-only `load` and `loadSolution`, checks `generator_seed = date`, then `src/puzzles/gears/verify-stored.ts` re-solves with `solveAll` and compares crank, figure and killer.
- SPEC §5.2.3 gained a "Daily diagrams (T036)" paragraph.
- New tests: `scripts/generate-gears.test.ts` (args, create, idempotence, seed survival, regeneration determinism), `src/puzzles/gears/verify-stored.test.ts`, `src/utils/london-time.test.ts`.

## Deviations and follow-ups

- **Deviation from "upserts":** a date that already has a `gear_daily` row is skipped rather than rewritten, because the seed path deletes and reinserts subtype rows, which cascades to players' `gear_attempts`. New dates still go through the upsert. Regenerating after a preset retune means dropping the rows first.
- The brief said gears `verify(content)` already exists on the module; it does not (`module.ts` has no `verify`). Content-file verification for gears is therefore a no-op today; the DB re-solve covers generated rows. Curated gear content (T044) will need a `verify` hook (it can call `verifyStored` on `diagramOf(content)`).
- Production has no step that runs `puzzles:gen-gears`, so dailies need a Vercel cron or a build step to be materialised there. Not in scope; follow-up for T043 or T070. The script must then be pointed at Neon with `DATABASE_URL_UNPOOLED` (never done here).
- `--days` is capped at 366 as a sanity bound.
