### AC5
Cycle 1: `LayoutCount` grew by 239 in 5 s, one layout per frame. A probe (`layout-probe.mjs`) showed that in Chrome any change to SVG geometry or to an SVG element's transform (attribute or CSS) forces a layout per frame; only transforms on HTML boxes (including a nested `<svg>` element) do not.

Fix: `board.tsx` is now an HTML board. The rings and victim are a static SVG. Each gear is an HTML box moved with a CSS `translate` in `cqw` units (the board is a size container, 1 unit = 0.5cqw). Its cog is an `<svg>` element turned with a CSS `rotate`, and the vision Xs are small `<svg>` elements counter-rotated through a `--facing` custom property. Meshes are 1-unit boxes with `translate rotate scaleX`. The scrubber's cog moves with `x` instead of `left`. Dashed mesh lines became faint solid lines (a dash pattern would stretch with `scaleX`).

Two more layout sources were found with trace invalidation tracking: writing the `data-slot` attribute (the shadcn styles select on it, so it is now `data-ring-slot`), and the sightlines being toggled by `display` in the paint loop (now rendered from the solver's `atConvergence` state, in the same commit as the status text). Pressing play also did its status update in a second commit; `onSettle(null)` now happens in the click handler.

Final: `layoutCountDuringClick: 2` (hover and the play-button commit), `layoutCountDelta5s: 8` over the 5 s of play after the click. Those 8 are the 1 Hz puzzle timer text (5), and the status line, hint and sightlines changing at 3 convergence stops. None are per frame. Total from before the click is 10.
