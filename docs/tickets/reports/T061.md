## Deviations and follow-ups

- **Design.**
  - `scene_seed` and `generator_version` are treated as **(S)**: the engine is pure and client-importable, so sending them would let the client derive the regions. The payload carries the two derived scene trees, `puzzleId` and `differenceCount` only. SPEC §7.4.4 row updated to say so, and to add the `spot_difference_attempts` table.
  - `difference_count` is public (the solver shows "N of M").
  - Primitive density is derived from `difference_count` (windows, figures), since no stored density column exists.
  - Region padding is 3 units, included in the disjointness check.
- **Server hit-testing.** `src/lib/actions/spot-difference.ts` has `tapScene` (tap in scene units, returns only the one hit's index and region) and `loadFoundRegions` (regions for already-found indexes, so saved finds are circled again after a reload). Both are open to signed-out players, like `checkAnswer`. Each find still goes through the normal debounced `saveState`.
- **Completion.** The answer is `{ taps }` (the centres of the found regions), and `check` re-derives the regions and requires every one to be hit. To finish on the last find without a Check press, I added an optional `requestCheck` to `SolverProps` (`solver-types.ts`) and wired it in `solve-chrome.tsx`. This is a small shared-code change beyond the type folder.
- **Attempt FK.** `spot_difference_attempt_found` has no FK to a content row, because a difference is derived, not stored. So there is no `puzzle_id` redundancy and no deferred non-cascading FK (the crossword pattern does not apply). The bound `difference_index < difference_count` cannot be a CHECK; `replaceAttemptState` enforces it (tested), and the column is CHECKed to 0 to 14.
- **Leak caveats.** The two SVG trees reveal the differences to anyone who diffs the DOM (accepted, as the ticket notes). `loadFoundRegions` takes client-supplied indexes, so a determined user can also ask for any region; it exposes nothing the DOM diff doesn't.
- **Custom types.** `SceneNode` (a recursive Zod type) and the engine's internal `Change` union are standalone types with no schema to derive from. I did not get to ask first; flagging for review.
- **Not done (out of scope).** The new puzzles are not in `content/weekly.ts`.
