## Deviations and follow-ups

- SPEC §7.4.5 edited: rows for `rota_attempts.puzzle_id`, `rota_attempt_swaps.puzzle_id` and `rota_clue_never_in_rank.puzzle_id`. SPEC §7.4.4 is unchanged.
- Natural keys, not redundancy: `rota_worker_squares.puzzle_id` (pk `(puzzle_id, worker_id, phase)`, with candidate key `(puzzle_id, phase, file, rank)` that stops two workers sharing a square), `rota_solution_swaps.puzzle_id` (pk `(puzzle_id, step)`) and `rota_clues.puzzle_id` (unique `(puzzle_id, position)`). SPEC §7.4.4 lists the squares pk as `(worker_id, phase)`; the extra `puzzle_id` is what enables the square uniqueness and the composite worker FK.
- SPEC column `rota_clue_max_swaps.max` is named `max_swaps` (avoids a reserved-looking word).
- Beyond the ticket: `unique (puzzle_id, name)` on workers; `step >= 1` and `worker_a <> worker_b` checks on swaps; `rank between 1 and 8` checks; `rota_clues` unique `(id, kind)` and `(id, puzzle_id)`; the require-subtype trigger also fires on `UPDATE OF kind` and skips clues deleted in the same transaction.
- Engine semantics (SPEC does not define them): `adjacent_only` means orthogonal neighbours at the time of the swap; `unpowered_square` means no swap involves a worker standing on that square; `max_swaps` caps the total sequence length; `never_in_rank` holds in every state including intended and final. All are prefix-checkable, so `solve` prunes. `solve` takes `{ maxSteps = worker count, cap = 2 }` and counts sequences, so with no `max_swaps` clue, swap-and-undo pairs count as extra solutions.
- Instigator ambiguity: an unordered swap does not say who instigated it. `openingGambit` returns `workerAId` of the first swap as instigator by convention, while the DB stores `rota_solutions.instigator_worker_id` (per SPEC) and `check` compares the answer's `instigatorWorkerId` to it, requiring it to be in the first swap. Whether to derive the instigator from swap order instead is a SPEC decision.
- `check` returns `{ correct }` only; a real `check` is implemented (pure, uses the engine). Content, `verify`, the solver UI and `puzzles:verify` coverage are left to T063; `Solver` is null. The `rota` row already existed in `content/lookups.ts`.
- Migrations: `20261002165816_rota_tables` (generated) and `20261002165816_rota_triggers` (custom), explicit FK names.
- Rota-only trigger functions follow T033: no `SECURITY DEFINER`, `search_path ''`.
