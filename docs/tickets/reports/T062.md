## Deviations and follow-ups

- SPEC §7.4.5 edited: rows for `rota_attempts.puzzle_id`, `rota_attempt_swaps.puzzle_id` and `rota_clue_never_in_rank.puzzle_id`. SPEC §7.4.4 rota row aligned with the schema in review (pk, candidate key, `max_swaps`, instigator trigger, `rota_attempts`).
- Natural keys, not redundancy: `rota_worker_squares.puzzle_id` (pk `(puzzle_id, worker_id, phase)`, with candidate key `(puzzle_id, phase, file, rank)` that stops two workers sharing a square), `rota_solution_swaps.puzzle_id` (pk `(puzzle_id, step)`) and `rota_clues.puzzle_id` (unique `(puzzle_id, position)`). SPEC §7.4.4 lists the squares pk as `(worker_id, phase)`; the extra `puzzle_id` is what enables the square uniqueness and the composite worker FK.
- SPEC column `rota_clue_max_swaps.max` is named `max_swaps` (avoids a reserved-looking word).
- Beyond the ticket: `unique (puzzle_id, name)` on workers; `step >= 1` and `worker_a <> worker_b` checks on swaps; `rank between 1 and 8` checks; `rota_clues` unique `(id, kind)` and `(id, puzzle_id)`; the require-subtype trigger also fires on `UPDATE OF kind` and skips clues deleted in the same transaction.
- Engine semantics (SPEC does not define them): `adjacent_only` means orthogonal neighbours at the time of the swap; `unpowered_square` means no swap involves a worker standing on that square; `max_swaps` caps the total sequence length; `never_in_rank` holds in every state including intended and final. All are prefix-checkable, so `solve` prunes. `solve` (changed in review) counts only the shortest valid sequences, capped at `cap = 2`, and `check` requires the answer to have the stored solution's length, so undo-padded sequences are neither counted nor accepted.
- Instigator: authored data (`rota_solutions.instigator_worker_id`). Changed in review: `openingGambit({ swaps, instigatorWorkerId })` returns the first swap with that instigator, or undefined if the instigator is not in it, and the deferred trigger `trg_rota_instigator_in_first_swap` enforces step-1 membership in the DB.
- `check` returns `{ correct }` only; a real `check` is implemented (pure, uses the engine). Content, `verify`, the solver UI and `puzzles:verify` coverage are left to T063; `Solver` is null. The `rota` row already existed in `content/lookups.ts`.
- Migrations: `20261002165816_rota_tables` (generated) and `20261002165816_rota_triggers` (custom), explicit FK names.
- Rota-only trigger functions follow T033: no `SECURITY DEFINER`, `search_path ''`.

For the orchestrator (not fixed: SPEC §5.1 is outside this ticket's editable sections):

- Record in SPEC §5.1 Mode C: the clue semantics (`adjacent_only` = orthogonal neighbours at the time of the swap; `unpowered_square` = no swap involves a worker on that zone; `never_in_rank` holds in every state, intended and final included; `max_swaps` caps the total sequence length), and the rule that the answer is the unique shortest valid sequence.
- SPEC §5.1's example clue "Each worker swapped at most once" reads per worker, but `max_swaps` caps the total. A per-worker cap of 1 makes every swap disjoint, so swap order could never be deduced. Total length is the workable reading, but a decision is needed if a per-worker kind is wanted.
- T063 `verify` must assert `solve(intended, final, clues)` returns exactly the stored sequence, comparing each swap as an unordered pair (solve orders each pair by id). `check` relies on the stored solution being the shortest.
- The DB does not enforce that every worker has both phase squares, or that the intended and final zone sets match. `placementFor` throws, and `verify` would catch it. Leave it to T063 content verification.
