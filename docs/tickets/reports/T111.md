## Design decisions

- **Table** `daily_puzzles (type_key, date, puzzle_id, generator_version)`: pk `(type_key, date)`, unique `puzzle_id`, composite FK `(puzzle_id, type_key)` to `puzzles (id, type_key)` with cascade, check version > 0. Migration `20261103035907_daily_puzzles`, additive only (renamed from drizzle-kit's random name before it ran anywhere shared). The generator name is the type key, so only the version is stored. SPEC §7.4.3 table list, §7.4.5 redundancy row and the seeding section updated.
- **Difficulty** cycles 1 to 5 by days since 1970-01-01, so a date's difficulty is independent of the run. The puzzle difficulty column is that value.
- **Slug** `daily-<type>-<date>`, title `Daily <date>`, no volume, `published_at` London midnight.
- **Type list** is `src/config/daily-types.ts` (sudoku). Another type joins by listing it; its generator must already be registered.
- **Write path** is `upsertPuzzle` in a transaction with the `daily_puzzles` insert (`src/lib/data/daily-puzzles.ts`). Existing dates are skipped.
- **Seed** excludes puzzles linked in `daily_puzzles` from removal. `gear_daily` untouched.
- **Verify** (`verifyDailyRows` in `scripts/verify-puzzles.ts`): slug, `published_at`, regeneration at the stored version, the type's `verify` (uniqueness re-solve), and an order-insensitive comparison of the stored payload with the regenerated one.
- **Cron** `/api/cron/daily-puzzles`, 00:10 UTC (after gears at 00:05), Bearer `CRON_SECRET`, today through +365 days per daily type. The first run on production generates about a year (about 30 s locally, `maxDuration` 300). The build does not generate dailies.
- Daily puzzles with past dates are not excluded from the public catalogue by volume; the daily UI is out of scope.

Decisions (made without the user, as delegated):

- **First production cron run, no cap per invocation.** Locally, `regenerate` takes 81 ms per sudoku on average (1.06 s at most), about 29 s for 361. Production evidence for the DB side: the first `daily-gears` cron wrote 366 gear dailies through the same per-puzzle transactions in 11.9 s (Neon `main`, `max(created_at) - min(created_at)` = 11.90 s, 2026-10-07 00:33). Even at 3 times the local CPU cost, that comes to about 100 s, against `maxDuration` 300. So no batching was added. On Hobby the cron fires within its hour (gears ran at 00:33 for a `5 0` schedule), so it can overlap the gears cron. That is safe: they use different tables, slugs and lock keys.
- **Build impact.** `db:seed` only gains a `NOT IN (select puzzle_id from daily_puzzles)` filter. The puzzle pages prerender every puzzle, so the production build gains about 366 pages. The latest production build rendered 745 pages in 40 s, so this adds roughly 20 s.
- **`puzzles:verify` cost.** With 366 dailies, the full run takes 51.5 s locally (`366/366 daily rows regenerate and are unique`). CI seeds a fresh database with no dailies, and the Vercel build does not run verify, so neither production nor CI pays this cost.
- **Migration.** It only adds a table, so the previous deploy runs unchanged on the migrated schema. If old code were rebuilt, its seed would remove the daily sudokus (no content file), and the cron regenerates them deterministically. An instant rollback does not re-run the seed.
