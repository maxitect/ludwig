## Design decisions

- **Registered: troix and kakuro** (`src/config/daily-types.ts`). Troix is by far the fastest. Railroad was also fast, but sudoku + troix + kakuro + railroad took about 193 s locally, too close to the 300 s limit if production is slower, so it was left out. With three types the first run is about 123 s locally, 2.4x headroom.
- No batching of the first backfill: the cron already writes missing dates only, is idempotent and lock-protected, so if a run did time out the next run would continue where it stopped and leave no partial state (each date is its own transaction).
- **Player wiring:** a daily is an ordinary published puzzle (slug `daily-<type>-<date>`, `published_at` at London midnight), so the existing puzzle page, catalogue and future-date 404 apply unchanged. Sudoku has no extra daily UI either, so none was added.
- **`puzzles:verify` fix:** kakuro's served payload derives its clues from the solution, so comparing the stored payload to `payloadSchema.parse(content)` failed on every kakuro daily (unrecognized key `digit`). `scripts/verify-puzzles.ts` now builds the payload from content for kakuro with `deriveClues`.
- SPEC §daily paragraph updated to name the registered types.
- `puzzles:verify` with 1098 daily rows takes about 148 s locally; CI seeds a fresh database with no dailies so its `db` job does not pay this.

## Deviations

- Chose three types (troix, kakuro) rather than the ticket maximum: the ticket allows at most three new ones, only two were registered to keep the first-run time safe. Recommended-option choice per the overnight instruction.
- Did not run the cron route itself locally; timings are from `puzzles:gen-daily` per type, which is the same `generateDailies` call the cron makes. Production check after merge.
