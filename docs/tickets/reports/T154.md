## Design decisions

- **Schema.** Migration `user_favourite_types_and_type_visits`: two new tables, composite primary keys, FK to `user` on delete cascade, FK to `puzzle_types`. No trigger or redundancy, so no custom migration. Additive, so it is safe against the previous deploy.
- **Visit recording** is a Server Action (`visitType`) fired from a small client component (`VisitRecorder`, `useEffect`) after hydration. It is mounted by `VisitSlot`, which sits in a `<Suspense>` and renders only when signed in. A page render, a prefetch or the cached catalogue never writes. A dynamic-slot write during render would have run on GET and on prefetch.
- **Cached pages stay static.** The catalogue functions only gained `publishedAt` and the daily relations. The favourite state is one `getFavouriteTypeKeys()` promise started at page level and awaited in per-card `<Suspense>` slots, the way `SolvedBadge` works. `toggleFavouriteType` revalidates only `/desk` (dynamic), so it causes no ISR writes. No new prerendered page.
- **New** is computed in the cached `getCatalogue` and `getTypeCatalogue` from `publishedAt` with `isNewlyPublished` (`src/config/new-puzzles.ts`, `NEW_WINDOW_DAYS = 14`). It excludes `daily_puzzles` and `gear_daily` puzzles. It is as fresh as the "minutes" cache life, which is the same staleness `isPublished` already has.
- **Desk shelf** is one RQBv2 query for favourites with each type's newest published puzzle, and one grouped SQL count of non-daily puzzles with `published_at > coalesce(visited_at, now() - 14 days)`. A type never visited uses the New window. Nothing is stored.
- **Toggle.** The existing `Toggle`, a Lucide `Star`, `primary` (red) when on. On a Collection card it sits outside the card's `<Link>` (absolutely positioned) to avoid a button inside a link. Signed out it is a link to `/sign-in?next=...`, a client component because `toggleVariants` is exported from a client module (a server-side call failed in the production build and was caught by the e2e).

## Deviations and follow-ups

- SPEC §7.4.3 lists the two tables and the New rule; PLAN §5.4 notes that `publishedAt` drives the New marker.
- The Collection "N new" badge counts every non-daily type puzzle in the window, so on launch content several types read "5 new". That follows the 14-day rule the ticket sets.
- Self-assessed visuals at 1280 and 390 in Paper and Ink (`.verification/T154/*-{type,collection,desk}.png`): no horizontal overflow, the toggle and badges stay on tokens.
- The e2e for AC4 is not automated: the type page and Collection read the cached catalogue, so a date change in the database does not show until the cache refreshes. The window is covered by a unit test, and AC4 was verified by hand after a rebuild.
