Those are the days writes and CDN requests jump; Nov 20, the day they did not play, is the lowest write day of the cycle (2.5K). It is a real player, not a crawler: nothing to block.

What one evening of play costs (last 24 hours, that IP):

- About 8.6K requests for `/favicon.ico` and `/apple-icon.png` from `ddg_win`, the DuckDuckGo for Windows favicon fetcher. Bot Protection challenges all of them, and they keep retrying. These count as CDN requests and write nothing to ISR.
- About 17K allowed requests from the browser. Each nav link (`/`, `/about`, `/puzzles`, `/reverse-chess`, `/casebook`, `/gears`, `/this-week`) was requested about 1.8K times, about the same number each. That looks like link prefetches on every page view or refresh, not people visiting those pages. The puzzle pages they played got tens to hundreds of requests each.
- The 30-minute log sample shows the write mechanism: a `/puzzles` view prefetches every type page in the same second, and every one older than the `minutes` cacheLife comes back `STALE` (`stale_time`), which starts a regeneration, which is an ISR write. The Observability ISR panel shows 635 time-based revalidations in 12 hours.
- One more purge path: `saveTheme` and `saveSettings` call `revalidatePath("/", "layout")`, so a theme or settings save marks every cached page stale (`REVALIDATED`, `delete_tag` in the log sample at 13:21 UTC). That is rare at today's user count (11 users, one with a non-system theme), but it grows with each user.

**Read:** ISR writes grow with page views because pages go stale after five minutes and every prefetch of a stale page regenerates it. One engaged player, on five evenings, takes the cycle from about 50% to about 100% of the limit. T159's fixes (prerender scope, batched deploys) worked; what is left is the `minutes` cacheLife and prefetch fan-out, which T159 is told to leave alone. AC6 fails as written.
